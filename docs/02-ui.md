# 02. UI

## Model

The compositor owns the terminal and lays out panes. The primitives below are part of the protocol, not tied to a specific library: every renderer implements them identically.

## Primitives

- **Pane** — a surface: a named cell buffer (`wl_surface`). A plugin declares a surface; the compositor allocates a slot for it.
- **Site** — a layout slot (`xdg_toplevel`) that a pane binds to. Layouts are swappable, like tiling schemes in Sway.
- **Status bar** — a layer above everything (`layer-shell`): active model, token budgets, workflow state, plugin roster.
- **Focus / input routing** — input is delivered to the focused pane; a click moves focus, as in a window manager.
- **Damage tracking** — a pane marks changed regions (`invalidate`); the compositor redraws only those, not the whole screen.

## OpenTUI conversation prototype

Run `npm run opentui:preview` in a terminal from a source checkout with
Bun 1.4.4 and installed workspace dependencies. This opens a local preview
with two independent agent conversations and a table from the workflows plugin.
The demo starts a sample workflow and uses a deterministic local provider.
It stores state in a temporary directory for the life of the preview.

1. In **Main**, submit `hold main` to keep a response streaming. Type a draft.
2. Press **F3** or click **Side**. Enter a message and submit with **Enter** or
   **Send**. **Ctrl+J** adds a newline. **F2** returns to the draft in Main.
3. Press **F4** for **Workflows**. Use **↑/↓** to select a row and **Enter** or
   a click to expand its details. Returning to a conversation restores its draft.
4. In a ready conversation, submit `request write`. Review the tool, reason,
   path and arguments in the approval card. **PgUp/PgDn** scroll the details.
   **Alt+Y** allows this one call and **Alt+N** denies it. The buttons also
   work with the mouse. The composer keeps your draft while you review.
5. Switch tabs while an approval is pending. Each waiting chat shows an
   **Approval** badge. Only the selected chat's card can answer its request.
   **Ctrl+C** closes the preview and declines outstanding requests.

The local approval example writes `main-note.txt` or `side-note.txt` inside
the temporary preview workspace. Each new write goes through the normal
tool permission policy.

The private `renderer-opentui` workspace owns rendering and native widgets.
The preview host translates core conversation events and plugin table updates
into its inputs. Selecting a workflow row returns that row's declared action
through the plugin's ordinary `ui.press` handler. The plugin owns expansion.
On a wide screen with negotiated Kitty graphics, the composer displays
the original idle or thinking Ghost. Set `AGENT_GRAPHICS=off` to hide it.

The shipped terminal still uses Ink. This preview covers the composer, agent
switching, one-call permission decisions and workflow row expansion. Full
wire-protocol support, settings, question dialogs, persistence across restart and release packaging are later migration
steps. [Migration plan](readiness.md#planned-opentui-migration--2026-11-13)

## Reference renderer implementation: Ink

React + Yoga flexbox: pane = `Box`, site = column/row, status bar = `Spacer` at the bottom. Scroll areas come out of the box in the new major Ink release: `overflow="hidden"` + `contentOffsetY` + the `useBoxMetrics` hook.

Starter layout:

```
┌──────────────────┬───────────────────────┐
│                  │  panes: agents        │
│  pane: session   │         tasks         │
│  (chat + stream) │         workflow      │
│                  ├───────────────────────┤
│                  │  pane: inspector      │
├──────────────────┴───────────────────────┤
│  status bar: model · tokens · plugins    │
└──────────────────────────────────────────┘
```

**Mouse:** the reference renderer parses SGR mouse sequences and forwards input
through the protocol. The compositor owns hit testing, focus, capture and
drag/resize. See [the terminal manual](../packages/app/README.md) for bindings
and [the visual bench](../tools/visual/README.md) for actual PTY verification.

The Ink renderer selects interactive repainting from its output stream's
`isTTY` flag. A real terminal continues to receive live frames with inherited
`CI` or `CONTINUOUS_INTEGRATION` flags; those flags do not turn the running
interface into an exit-only frame. A redirected renderer output stream retains
static final-frame output.

## The Claude Code lesson

Claude Code started on stock Ink and rewrote the render engine: the stock version allocates one object per terminal cell per frame (~24,000 objects at 200×120 every 16 ms) and diffs whole strings. Their fork: typed arrays instead of objects, double buffering, cell-level dirty tracking.

**Conclusion:** Ink's component model (React + Yoga) is permanent; the engine beneath it is a consumable that can be replaced without rewriting components. Hence the hard rule: the compositor consumes the core **only through the versioned protocol**, even when living in the same process with it. The seam matters more than the framework.

## Swappable renderers

One protocol — any number of implementations:

- **headless** — JSONL over stdio or a unix socket: tests, scripts, external tools;
- **TUI** — Ink (the reference);
- **web** — a future implementation could transport the same protocol over WebSocket; a web renderer is not currently shipped.

External tools (fzf, tmux, a custom dashboard) become clients of the compositor — the "netlink move" that no existing CLI agent has.
